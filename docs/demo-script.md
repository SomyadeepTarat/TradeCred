# TradeCred demo — Milestone 9

Use fictional data and explicit `LEDGER_BACKEND=mock` unless a real Drunix network is
provisioned. Mock receipts begin `MOCK-`; disbursements begin `MOCKPAY-`. No funds move.
The signing service generates actual Ed25519 signatures and the API verifies every event.

## Start

1. Complete README installation and configure the private `.env`, including `JWT_SECRET`
   and `DEMO_PASSWORD`. Preserve existing credentials and keep Docker Desktop running.
2. Run `make install` on first setup, then `make demo`.
3. Open http://localhost:3000. All seeded users use the password set when first created.

`make demo` preserves existing keys, creates a private simulator token if missing, starts
API/web/PostgreSQL and the optional sandbox signer, seeds identities, then creates fixtures
through the authenticated APIs. It does not reset records. `make seed-fixtures` resumes
interrupted fixture setup and preserves assets already beyond their intended starting state.
The generated PDF/metadata examples and receivable IDs are in ignored `data/demo/`.

Fixtures:

| Invoice | Starting state | Use |
| --- | --- | --- |
| EXP-2026-1042 | FINANCE_AVAILABLE | Flagship walkthrough: Alpha Looms Demo, buyer BUYER-DE-001, EUR 10,800 |
| DEMO-VERIFIED-01 | VERIFIED | Register/open a verified invoice |
| DEMO-FINANCED-01 | FINANCED | Duplicate financing and settlement shortcuts |
| DEMO-REALIZED-01 | REALIZED | e-BRC eligibility and closure shortcut |

Asset IDs are generated by the normal application workflow; use the displayed ID, not
an invented TC-2026-001. There is no FX conversion: the advance is EUR 9,750 against a
EUR 10,800 invoice. The flagship invoice date is 2026-09-21 and due date 2026-11-25.

## A — Happy path

1. Sign in as `exporter@tradecred.demo`. Open EXP-2026-1042 and show fingerprint,
   document hash and recorded verification/registration. For the upload portion, use
   **Create receivable**, choose a new invoice number and upload a demo PDF; submit it,
   sign in as `admin@tradecred.demo` to verify, then exporter to register and open it.
2. Sign in as `bank@tradecred.demo`; open the flagship from available receivables.
   Submit EUR 9,750, 250 basis points, 60-day tenor and a future expiry.
3. Optionally sign in as `nbfc@tradecred.demo` to submit a competing offer.
4. As exporter, review and accept the Cedar Finance offer. Show LOCKED, the agreement
   hash and rejected competing offer. Only one institution controls the financing state.
5. As the winning bank, use **Simulate disbursement**. Show FINANCED and the explicit
   **NPCI Payment Adapter — Sandbox Simulation** receipt.
6. As `settlement@tradecred.demo`, select the asset in **Settlement simulator**.
   Enter 1080000 minor units, EUR, and IRM-DEMO-938291. Use **Send Valid Signed Event**.
   Show PAYMENT CONFIRMED and the ledger receipt. TradeCred consumed a confirmation;
   it did not send money.
7. As admin, open the asset. Click **Mark realized**, **Mark e-BRC eligibility**, then
   **Close receivable**. Show the complete recorded journey and
   SELF_CERTIFICATION_PENDING. Eligibility and closure do not issue an e-BRC certificate.

## B — Duplicate financing attack

1. After financing the flagship, sign in as the second institution.
2. Open **Registry checker**. Its defaults match the flagship; click **Check registry**.
3. Show **Duplicate receivable already financed**, the existing asset, state, fingerprint
   and backend. No private commercial terms are returned. The second institution cannot
   submit another offer or disburse against the financed asset.
4. As exporter, try uploading `data/demo/EXP-2026-1042.pdf` with the matching metadata
   from its JSON file, including the same invoice number. The API rejects the duplicate
   even if the PDF filename changes. Admin activity records the duplicate rejection.
5. A clear registry result only covers participating systems; it is not credit approval
   or a guarantee against off-network financing.

## C — Fake settlement and replay

Run this before settling the flagship, or use DEMO-FINANCED-01.

1. As settlement operator, select the financed asset and use **Send Invalid Signature**.
2. Show SIGNATURE REJECTED. Refresh the exporter detail: it remains FINANCED.
3. Use **Send Valid Signed Event** with the correct full invoice amount and currency.
4. Show PAYMENT CONFIRMED, then click **Replay Event**. The exact same signed bytes,
   event ID, nonce and timestamp are resubmitted and rejected as PAYMENT EVENT REPLAY.
5. As admin, open **Audit & security** and show the signature rejection, replay rejection,
   successful transition and participant activity. Other roles cannot read the audit APIs.

The replay button retains the last submitted event in the current page. After the five-minute
freshness window, replay may be rejected as PAYMENT_TIMESTAMP_EXPIRED instead. Unknown
ledger outcomes are labeled unknown; restore connectivity and replay the exact event to
recover. Never interpret a timeout as success or rejection. Avoid refreshing before recovery.

## Validation and remaining scope

Run `make test`, `make test-integration`, `make lint`, and `make test-e2e`. Browser tests
exercise competing finance, the registry warning, invalid/valid signatures, replay, closure
and security feed using an isolated database and real temporary signing keys.

`make reset` remains Milestone 10 and intentionally exits nonzero. To demonstrate a new
cycle without deleting existing records, upload a new invoice number. Keep the development
stack private. Stop it with `docker compose --profile demo down`; data is retained.
`make dev` without the demo override disables the simulator API unless SIMULATOR_ENABLED
was explicitly set true in `.env`. Existing keys and signatures remain private.
